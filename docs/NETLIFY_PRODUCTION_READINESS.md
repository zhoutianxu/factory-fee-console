# Netlify 生产化上线说明

## 当前结论

当前系统已经接近本地 1.0 版本，但还不能“原样”作为多人在线系统部署到 Netlify。

原因是当前系统依赖：

- Flask 服务端页面
- 本地 SQLite 数据库
- 本地文件上传、下载和输出目录
- 本地配置 YAML 文件

这些能力在本地运行很合适，但 Netlify 的默认部署模型更适合静态前端、无服务器函数和外部持久化服务。Netlify Functions 的运行环境不能把本地磁盘当成长期可靠的数据存储。

## 如果要供用户使用，推荐上线架构

### 1. 前端

部署到 Netlify：

- 页面导航
- 上传表单
- 配置表版本库界面
- 计算流程可视化界面
- 执行计算任务中心
- 计算结果与加工费导出页面

### 2. 后端接口

迁移为 Netlify Functions 或独立 API 服务：

- SAP 文件上传
- 配置表版本上传
- 计算流程保存
- 执行计算
- 结果查询
- 加工费导出
- 日志查询

如果计算任务可能超过 60 秒，更适合拆成后台任务服务，而不是同步 Netlify Function。

### 3. 持久化

必须从本地文件迁移到云端：

- 数据库：Postgres、Neon、Supabase 或其他云数据库
- 文件：Netlify Blobs、S3 或其他对象存储
- 导出文件：对象存储，并记录下载链接和导出历史

### 4. 权限与审计

正式给用户使用前建议补齐：

- 登录
- 用户角色
- 上传、删除、执行计算权限
- 操作日志
- 数据备份
- 异常恢复

## 可分阶段交付

### 阶段 A：发布说明页

把当前 Netlify 页面作为公开说明入口，说明系统能力、使用边界和本地试运行方式。

### 阶段 B：云端 MVP

将前端部署到 Netlify，将数据和文件迁移到云端存储，只保留核心流程：

1. 上传 SAP
2. 上传配置表版本
3. 选择流程与版本
4. 执行计算
5. 查看结果
6. 生成加工费导出

### 阶段 C：生产可用

补齐权限、审计、备份、并发控制和异常恢复后，再给更大范围用户使用。

## 不建议的上线方式

不建议直接把当前本地 Flask + SQLite + 文件目录版本包装成 Netlify 在线应用。这样短期看似能访问，但数据持久化、并发、权限和文件安全都会有风险。
